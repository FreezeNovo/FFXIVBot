## Problem Statement

群员已经能查询国服活动，所有者也能配置国服摘要和维护提醒，但还不能可靠订阅通用公告、同时接收国服和 NA 信息。当前摘要直接读取缓存，无法说明每项活动最后何时核实，也不会因为数据过旧而停止主动展示。所有者需要在本机完成配置，并在信息缺失或投递失败时看见可定位的原因。

## Solution

沿用现有独立 Python 应用、SQLite 与唯一 QQ 薄网关，补齐三条行为链：

1. 列表发现 → 文章版本与机械差异 → 每群订阅资格 → 即时/汇总/离线补发 → 现有投递账本。
2. 国服与 NA 正文 → 带证据的活动/维护时间 → 独立区域策略 → 共用查询、预览与渲染。
3. 摘要前复查 → 逐活动核实状态 → 到点生成 → 警告、排除或一次暂停提示 → 可恢复投递。

## User Stories

1. US01：作为所有者，我希望用分钟刻度调整新闻发现周期，以便控制时效与请求量。
2. US02：作为所有者，我希望列表发现与已知活动详情复查独立运行，以免短周期导致全量正文重复抓取。
3. US03：作为群员，我希望订阅启用后收到新公告，以便及时查看官方信息。
4. US04：作为群员，我希望启用、重新开启或新增范围时不被历史公告刷屏。
5. US05：作为所有者，我希望发布时间缺失的文章可核查，以免首次发现时间冒充官方发布时间。
6. US06：作为群员，我希望文章内容变动时收到更新提示，并自行判断变化的重要性。
7. US07：作为群员，我希望纯 HTML 样式和无意义空白变化不会重复通知。
8. US08：作为所有者，我希望保留文章原始版本及机械差异，以便解释更新通知的依据。
9. US09：作为群员，我希望旧文章首次出现只建立基线，后续真实内容变动才通知。
10. US10：作为群员，我希望同一文章发送前反复修改时只看到最终版本。
11. US11：作为所有者，我希望选择即时或每日汇总，且无新增内容时保持静默。
12. US12：作为群员，我希望离线恢复只补最近有效范围内的遗漏，并以汇总避免刷屏。
13. US13：作为所有者，我希望关闭订阅后未发送的消息立即失去发送资格，保留审计历史。
14. US14：作为所有者，我希望同群选择国服和 NA，并为三个消息流分别选择范围。
15. US15：作为群员，我希望区域标识清楚、摘要按区域分组，不把不同地区活动混在一起。
16. US16：作为群员，我希望看到 NA 官方标题、中文分类和北京时间，并能追溯原文及时间证据。
17. US17：作为群员，我希望 NA 维护沿用独立公告、提前提醒和时间更新的规则。
18. US18：作为群员，我希望每日默认看到正在进行、未来七天开始及临近结束的活动。
19. US19：作为群员，我希望来源正常且没有活动时保持静默，手动查询时得到明确空结果。
20. US20：作为群员，我希望摘要前重新核实活动，不只重复旧缓存。
21. US21：作为群员，我希望少数官网请求迟迟不结束时仍按时获得可用摘要。
22. US22：作为群员，我希望核实失败或数据变旧时看到警告，过旧信息停止主动展示。
23. US23：作为所有者，我希望一项活动或一个区域失败不阻断其余有效结果。
24. US24：作为群员，我希望持续故障只提示一次暂停，恢复后正常收到摘要。
25. US25：作为所有者，我希望手动查询仍能查看带警告的最后有效记录，且预览不冒充成功投递。
26. US26：作为所有者，我希望重启、重复唤醒和未知发送结果不会导致重复消息。
27. US27：作为所有者，我希望升级后已有群策略、授权、来源快照和投递历史完整保留。
28. US28：作为所有者，我希望能定位失败的来源、文章、阶段、原因及最终处理结果。
29. US29：作为维护者，我希望离线验证全部行为，并将真实群验收限定在明确授权的目标和消息预算内。

## Implementation Decisions

本节约束交付方式；完整架构设计归 [ARCHITECTURE](../../ARCHITECTURE.md)。不规定尚未核验的上游字段，不预先写死迁移后的 schema 版本号。

### 应用边界与测试入口

- 复用 CoreApplication 的服务装配、工作流 tick/preview、CommandService 和 MessagingPort。优先让一个测试从策略写入、fixture 刷新、可控时钟唤醒走到 fake MessagingPort 可见输出。
- 来源编排移到应用/runtime 边界；NoneBot 只注册生命周期和转接事件。HTTP 不进入消息 handler、renderer 或领取事务。
- 复用现有 HTTP transport、SQLite 备份和迁移机制；默认不引入新依赖、调度服务或前端框架。需要额外依赖时必须证明现有方案不足并完成许可、锁文件和部署评估。
- 来源周期等应用级运行设置由本机 WebUI 管理并持久保存；每群区域、分类、开关和发送时间保留群级策略。具体复查提前量按有界请求预算确定并文档化，不改变到点不继续等待的已确认行为。

### 文章与公告

- 来源稳定身份、原始内容版本、规范比较版本、群级对照基线和最后确认发送版本分别建模；标题、URL、消息文本不充当业务身份。
- 指纹覆盖产品指定内容，规范化有版本。标题单改不能被正文 hash 的快路径漏掉；只变样式/空白可留原始版本，但不产生通知。比较图片引用，不下载图像做视觉或语义比较；同一引用地址下的图片字节替换不在该机制的检测能力内。
- 文章抓取有效与活动时间解析有效是不同结果：没有活动时间的普通文章仍可通知，已知活动解析失败不能刷新其核实成功时间或删除旧活动。
- 订阅按群、区域及分类范围保存生效点。重新开启或新增范围不改写持续开启范围的历史；首次旧文建立基线，不伪装为新公告。
- 公告版本变动记录与待规划状态持久化，避免保存观察后崩溃导致漏通知。派发成功后才推进该群的已发送基线；未知结果不能被当作已送达，也不能绕过账本重新装入补发批次。
- 同一文章未开始发送的版本可合并，已开始投递的批次冻结。A→B→A 在群已收到 A 且 B 未开始发送时无净变化；如果 B 已确认发送，再回到 A 是新的变动，不能被旧 hash 的历史去重误抑制。
- 汇总与离线补发使用持久批次、成员及分页进度；同一条资格记录不能同时被即时流和补发汇总发送。72 小时边界必须基于保留的资格时间证据，不得通过重启、重试或重新导入延长；原文发布时间与更新被观测时间不可混称，证据不足遵循来源退化规则。
- 维护归独立流；新公告不能重复搬运同一维护提醒。现有维护起止时间比较继续有效，不因延期语义识别而移除。

### 多区域与 NA

- 旧单区域策略迁移为单元素集合，保持原开关、显式窗口、授权和业务身份。新增能力不自动订阅 NA；尚未有真实实现的区域不能在 UI 中被暗示为已支持。
- 每条待发送消息保留其所覆盖的区域及业务对象，以便发送前复核。删除一个区域后，不得继续发送已排除区域的旧内容，也不得清空其他区域历史。
- NA 时间解释必须先经过 01 的真实契约核验和固定样本；保存原文、来源时区、UTC、显示区域、parser 版本及证据。跨年、夏令时、日期精度和缺失时区不能靠机器本地时区补齐。
- 单篇文章可以产生多个断言；先沿用单来源内保守关联，避免顺手引入跨文章自动合并或完整 CanonicalEvent 重写。

### 复查、新鲜度与投递

- 活动核实记录与来源整体健康分开。单篇内容未变且既有解析有效时，成功复查也更新其核实时间；列表成功或同批另一篇成功不能更新它。
- HTTP 304 只有验证了该活动对应的有效内容版本才可视为复查成功；列表 304 不等于所有正文重新核实。新正文解析退化时保留原活动与最后有效核实时间，并记录最近失败。
- 摘要准备按计划窗口识别待展示活动，合并同源文章的重复复查。复查结束后重新查询；晚到结果不能改写已开始投递的批次或形成当天第二份摘要。
- 实施必须覆盖启动已晚于预查时刻、发送时刻被修改、进程重启、正常后台刷新与预查重叠、发送前资格改变。不能为了等待上游阻塞全部群或调用线程中的事件循环。
- 新鲜度评估返回结构化结果，区分有效、警告、过旧、未核实及确实无活动。旧库缺少可信逐活动时间时不伪造“刚核实”；保留手动查看能力并在首次复查后恢复正常判断。
- 全量过旧的暂停提示拥有持久故障周期身份及业务幂等键；未知发送结果遵循现有规则。恢复结束该周期，下一次真正的新故障可重新提示；单一区域退化不阻断另一有效区域。
- 活动摘要仍遵守群本地日期去重与当天截止；所有者改变策略后要在实际发送前再核验。未开始发送的延期批次不得绕过当前新鲜度或区域策略；已有投递开始的批次保持冻结语义。

### 迁移与可观测性

- 每个改变存储的任务自带可重复迁移与固定旧库测试；11 只负责组合迁移和发布收口，不替前面的任务补欠账。
- 从当前 schema 16 保留来源、策略、授权、候选和 attempts；中间版本重复升级、失败后重试、备份恢复后再迁移都要可验证。旧日程键与历史已发送窗口不能生成重复消息。
- P3 记录源/文章/内部目标身份、阶段、错误类别、安全原因摘要、核实时间与退化动作；业务失败即使已转成 DTO 也要可诊断。控制台、文件留存与 WebUI/账本的职责应明确，避免只打印外层异常。
- 日志与故障 UI 不泄露连接凭据、真实 provider 目标标识或完整请求敏感内容。预览、migration preview 和测试不能创建真实投递成功记录。

### 契约与实施风险

- 01 必须核实 NA 正文覆盖、稳定 ID、时区/日期精度、更新发现与回溯范围。若真实契约与产品目标有冲突，记录证据并阻塞受影响任务，不能猜字段或把不支持能力标为完成。
- 15 分钟是配置默认周期，不是官方 SLA。源限流、分页完整性和没有正文时间的文章要分别处理，不靠扩大请求量掩盖缺口。
- 图片引用相同而远端图片内容改变、列表不披露旧文章修改等属于具体观测能力限制，必须在来源契约及实现验收中明确，不将抓取成功误解为穷尽所有更新。
- 每个任务只调整必要边界。应用服务当前依赖 StateStore 不构成全仓仓储抽象重写的理由。
- 12 的授权不从历史真实测试继承；本轮编写规格的请求不授权发送消息或迁移正式库。没有授权时，11 的离线完成与12 的待验收状态分别报告。
